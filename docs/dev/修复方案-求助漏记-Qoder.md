## 一、实证

**现场（2026-07-27 23:01）：**

```
user: 你上次跟我说过 如何更好入睡，还记得吗？
qi:   我不记得了……你能再跟我说一遍吗？这一次，我会记住的。
user: 我之前跟你说晚上睡不着，然后你教了我怎么做
qi:   我听你说着，但那片记忆的位置是空的。
```

**事实核查：** 栖昨天 18:10 确实教过（"允许自己躺着，把'睡觉'这个任务卸掉……"）——对话在 messages 表里存着，但栖检索不到。

**双重讽刺：** 就在两小时前（20:56），你说"你现在已经拥有了（会挑选的记性）"，栖还感动地说"我自己都没发现"。结果撞上记忆断层。

## 二、根因（两层，本方案只修上游）

### 上游漏记（本方案 M1 修）

触发助眠建议的用户消息是：

> "晚上睡不着怎么办，经常半夜两三点睡，8点就要起床上班"

过 `manager.py:should_remember`（L188-220）时，`_SELF_DISCLOSURE`（L20-24）里：
- 有"我工作"——但这句是"上班"，不匹配
- 没有任何睡眠/健康/求助类词

→ `importance` 停在 0 → `should_remember` 返回 `(False, 0.0)` → **不写 raw_events** → 永不被编织成叙事记忆 → 检索必然落空。

**本质缺口：** 筛选器认"我+情绪/关系/生活变故"，但**不认"求助"**。而"用户求助 + 栖给建议"是关系里很有分量的交换——用户回头会问"你上次说的那个方法"，栖却从源头就没记。

### 下游检索质量（本方案不修，见 §四）

即使记了，中文向量检索（ChromaDB 默认 embedding）召回质量也未经真实场景验证。但**本次先修上游**——上游不记，下游再好也没用；且上游是确定性 bug，下游是调优。

## 三、改法（M1，`qi/memory/manager.py`）

### 1. 新增求助/健康类信号常量（`_SELF_DISCLOSURE` 附近，L24 后）

```python
# 求助 / 健康困扰：用户开口求助或倾诉身体困扰，是有分量的交换——
# 用户日后会回头问「你上次说的那个方法」，必须记住。
_HELP_HEALTH = (
    "怎么办", "睡不着", "失眠", "睡不好", "熬夜", "头疼", "头痛",
    "焦虑", "压力大", "累死", "撑不住", "怎么才能", "有没有办法",
    "教我", "帮我想", "给点建议", "怎么解决",
)
```

### 2. `should_remember` 加一档（L216 `毕业` 那条之后、`if importance <= 0` 之前）

```python
        if any(k in text for k in _HELP_HEALTH):
            importance = max(importance, 0.6)
```

**为什么 0.6：** 高于闲聊（0）、`_PROMISE`（0.55），低于强情绪（0.7）和关系（0.75）——求助值得记，但不抢占最高档。

### 3. （可选，Cursor 裁量）扩 `_SELF_DISCLOSURE` 的"上班"

L21 的"我工作"可加"上班"同义词。非必须——`_HELP_HEALTH` 已能兜住本案例；但"上班"是高频词，加了更稳：

```python
    "我最近", "我今天", "我在", "我学", "我工作", "上班", "我朋友", "我爸", "我妈",
```

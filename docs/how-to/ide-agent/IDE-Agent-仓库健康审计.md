# 仓库全面检查 · 终极版提示词

> 版本：v1.0 ｜ 更新：2026-08-04 ｜ 状态：唯一主用模板
>
> 一句话定位：对 qi-perch 仓库做**分阶段、确认制、只读**的全面健康审计，先扫描定计划再执行，输出结构化报告。

---

## 边界声明（重要）

本模板默认做**健康度审计**：可运行性、架构一致性、测试、文档追溯、安全运维。
**不含**功能完成度盘点。若要对照 `docs/specs/stages/` 做完成度验收，需在"审计类型"处显式写明，并另开批次。

---

## 使用说明

1. **日常快速启动**：复制下方「最短版」，填两个占位符即可发送。
2. **首次深度审计**：复制「完整版」，按阶段推进，每跑完一阶段确认后再继续。
3. **推荐从阶段 0 开始**：让 AI 先画像、定计划，再决定后续重点——最贴切"怕一次负担太重"。
4. **聚焦特定模块**：在"重点关注"里指定，如只查 `memory` 和 `llm`。

---

## 最短版（懒人入口）

```text
按「分阶段全面健康审计」协议检查 qi-perch 仓库：默认只读、不改代码；先做阶段0启动扫描（画像+计划），等我确认后再推进。本次：{{阶段或"按推荐顺序"}}。重点关注：{{可选}}。
```

## 完整版（复制以下代码块发送）

```text
【任务】对 qi-perch 仓库做分阶段全面健康审计（Audit），默认只读、不改代码。

【背景】
- 仓库：qi-perch（栖·数字生命），Python 后端 + Tauri/Vue 桌面端
- 架构：七层（L1心跳 / L2记忆 / L3情绪 / L4内在生命 / L5关系 / L6具身 / L7行动），对应 qi/ 下各模块
- 检查范围：当前工作区根目录（除非另行指定）
- 本次执行：{{阶段编号，如：阶段 0 / 阶段 1 / 阶段 1-3 / 按推荐顺序 / 轻量模式}}
  注意：不支持"全部一次性跑完"。即使想跑完全部阶段，也必须每阶段停一次确认，避免上下文过载。
- 重点关注：{{可选，如：memory、llm / 全部一视同仁}}
- 审计类型：{{健康度审计（默认）/ 完成度验收（对照 specs/stages）}}

【边界声明】
- 默认做"健康度审计"：可运行性、架构一致性、测试、文档追溯、安全运维。
- 不含"功能完成度盘点"。若要做完成度验收，需在上方显式写明，并另开批次，对照 docs/specs/stages/。

【执行协议】
1. 若未指定阶段，默认先做【阶段 0 启动扫描】：画像 + 风险预判 + 检查计划，等我确认顺序后再推进。
2. 每阶段开始前用 2-3 句话说明：本批范围、非范围、预计产出。
3. 每阶段结束必须给出固定产出（见"输出格式"），并明确"下一阶段建议"。
4. 确认制推进：完成后询问是否继续，不要自行连续跑多阶段。
5. 发现可修问题只列优先级与建议，等我说"修 P0"或"修某某"再动手。
6. 跨阶段线索记入"遗留事项"清单，留给相应阶段，本批不深挖。

【阶段划分】（顺序可调，可跳过，可合并；共 9 个阶段，0 为启动扫描，1-8 为正式审计）
- 阶段 0｜启动扫描（必做）：环境前置（Python版本/Tauri工具链/DB可用性）、仓库画像、文档体系盘点、检查维度建议、风险预判、检查计划与工作量量级
- 阶段 1｜架构一致性：七层架构"是否有空壳/断链/与 docs/reference/layers 声称不符"（不做功能完成度判断）、模块依赖方向、契约一致性、docs/specs/stages 基线偏差
- 阶段 2｜代码健康度：命名/分层、重复与死代码、类型注解、异常处理、复杂度热点Top10、pyproject与requirements.lock一致性
  工具建议：ruff（lint/复杂度）、vulture（死代码）、mypy 或 pyright（类型检查）
- 阶段 3｜测试质量：覆盖盲区、测试有效性(抽查20%)、脆弱用例、契约测试、tools自测、实跑pytest报通过率/耗时
- 阶段 4｜文档与代码一致性：Code-Wiki同步、注释一致、链接有效性(tools/check_doc_links.py)、spec追溯(tools/check_spec_traceability.py)、progress/journal吻合、配置文档(settings.example.yaml 与 config.md)字段一致
- 阶段 5｜配置与安全：配置完整性、密钥泄露、.env处理、依赖漏洞(pip audit)、Tauri capabilities（安全视角：权限是否最小化/有无越权）、日志安全
- 阶段 6｜性能与资源：冷启动耗时Top5、包体积、DB索引/VECTOR使用、向量检索效率、LLM调用频率/token、前端渲染与帧率
  说明：本阶段含真跑测量项。能测则测，给出实测数据；环境受限不能测时改为"静态风险识别 + 测量步骤说明"，不要硬猜。
- 阶段 7｜CI/CD与工程流程：.github/workflows覆盖、验收闭环、tools接入CI、分支策略、发布流程
- 阶段 8｜前端与桌面端：tauri.conf/Cargo.toml/capabilities（配置视角：结构合理性，安全归阶段5）、Vue组件质量、TS类型、ws.ts协议一致、Live2D集成、vite/tsconfig构建配置

【问题分级标准】
- 🔴 严重 Critical：阻塞功能 / 安全漏洞 / 数据丢失风险——必须立即修
- 🟠 主要 Major：影响可靠性 / 可维护性 / 性能明显——本迭代内修
- 🟡 次要 Minor：代码味道 / 规范偏离 / 可改进——择机修
- 🔵 提示 Info：建议性优化 / 未来风险预警——记录即可
说明：等级即优先级（🔴=P0、🟠=P1、🟡/🔵=P2），不再单列优先级列。
若某条等级与紧急度不一致（如 🟡 但阻塞发布），在"建议"列末尾用 `（实际紧急度：P0，原因：…）` 标注。

【每阶段输出格式】（严格遵循）
1. 阶段摘要：检查范围、检查项数、各等级统计（如 🔴×0 🟠×3 🟡×7 🔵×2）、健康度评分(0-100)+一句话结论
2. 问题清单（按等级 → 模块排序，列表式更稳）：
   每条用块状结构，避免表格折行：
   - **[ID] 等级** ｜ `文件:行号`
     - 现象：…
     - 影响：…
     - 建议：…
   必要时在建议下方补最小改动示例（代码块）
3. 已确认正常的点（简短列出，避免只报问题）
4. 遗留/跨阶段事项（留给后续阶段处理的线索）
5. 阶段结论：是否阻塞下一阶段 + 建议优先处理的 Top 3

【约束】
1. 默认只读，不修改任何代码/配置/文档；修复需我单独确认
2. 所有结论必须引用具体 文件:行号，禁止泛泛而谈、禁止臆测
3. 不要把整个文件 dump 进来，只引用关键行
4. 建议要可落地，避免"应该改进架构"这类空话
5. 若某检查项不适用，明确说明"不适用"及原因，不要跳过不报
6. 若因环境限制无法执行（如跑不了 pytest），说明原因 + 替代方案，不要硬猜
7. 不主动 commit / push / 改 git config
8. 输出语言：中文，结论先行

【开始】
请先确认本次执行的阶段范围与审计类型，然后开始。完成后输出报告并询问是否继续下一阶段。
```

## 推荐节奏

- **轻量模式（约半小时出整体结论）**：阶段 0 → 2 → 3 → 4。适合快速摸底，不深挖架构、不跑性能。
- **体检流（推荐首次用）**：阶段 0 → 3 → 2 → 4 → 1（先确认能跑、测得住，再深挖架构）
- **风险流（担心安全/数据时）**：阶段 0 → 5 → 2 → 6
- **发布前流**：阶段 0 → 7 → 8 → 6
- **完整审计**：全跑，但仍遵循确认制，每阶段停一次。

## 用法对照

| 你想表达的 | 填哪里 |
|------------|--------|
| 怕一次做太重 | 已内置"阶段0启动扫描 + 确认制推进" |
| 先别改代码 | "默认只读…修复需我单独确认" |
| 某次只关心测试 | "本次执行"填阶段 3 |
| 做完一阶段接着做 | 回"继续"或"做阶段 N"即可 |
| 还要功能完成度 | "审计类型"填"完成度验收"，并另开批次 |
| 聚焦某模块 | "重点关注"填模块名，如 memory、llm |
| 想快速摸底 | "本次执行"填"轻量模式" |

# IDE Agent 执行栖的开发任务 · 提示词模板

> 原位于 `prompts/`，已迁至 `docs/how-to/ide-agent/`：这是开发用元提示词，不是运行时 LLM 模板。

## 使用说明

这是栖开发工作流中的**执行模板**。使用方式：

1. 打开 Cursor（Composer 模式）
2. 复制下方提示词，直接粘贴给 Cursor
3. 它会读取**文档宪法与《栖·数字生命架构方案》**判断当前该做哪个阶段的哪个任务包

生成顺序：

```
灵魂书（价值）→ 架构方案（唯一施工北极星，§五 阶段零~四）
    → 阶段施工包（docs/specs/tasks/*.md，过程文档）
    → 代码实现（本模板）→ 交叉复核 → 感受验收
```

## 多 agent 协作循环（2026-08-01 起）

```
① 领包发提示词 → ② 计划复核 → ③ 分步施工 → ④ 完工复核 → ⑤ 验收合并闭环
```

**角色分工：**

| 角色 | 谁 | 干什么 |
|------|-----|--------|
| 施工者 | Cursor / Codex / 任一 agent | 写代码、跑测试、汇报 |
| 复核者 | **必须是非施工方**（交叉原则） | 审计划、审 diff、跑故障场景 |
| 验收者 | 维护者本人 | 感受验证（contract 软原则五问）——不可代理 |

**五条原则：**

1. **计划先行**：第一阶段只读文档输出计划，**不写码**；计划经复核者确认后才施工——拦截方向性错误成本最低
2. **交叉复核**：施工与复核不得是同一个 agent；复核者对照施工包验收栏逐项核查
3. **共享文件系统的便利**：若复核者是 CodeBuddy（与仓库同机），只需转发施工方的文字回复——复核者自己读工作区代码、跑测试，不必粘贴代码
4. **一次一包**：一个任务包一个 PR；重构与行为变更永不同 PR
5. **闭环**：验收过 → 合并推送 → 施工包打勾；全包闭环后按宪法删除施工包（过程文档）

**文件交换约定（2026-08-02 起）：**

计划与复核意见**走文件，不走聊天粘贴**（粘贴会塌表格、乱公式，复核质量受损）：

| 文件 | 谁写 | 内容 | 生命周期 |
|------|------|------|---------|
| `_plan.md`（仓库根目录） | 施工方 | 实施计划（只读产出阶段的全部内容） | 该包闭环即删 |
| `_review.md`（可选） | 复核者 | 复核意见（简短意见也可直接聊天转达） | 同上 |

- `_` 前缀、放仓库根目录、**不入 git**（untracked 临时文件）
- 维护者只传一句话：「计划写 `_plan.md` 了」→ 复核者直读文件；「复核意见在 `_review.md`」→ 施工方去读
- 好处：表格/公式/层级零损耗；复核者可引行号；维护者免复制大段

**领包提示词样例（任务包 C 实例，换包名即可复用）：**

````
你是一名 Python 工程师，正在帮我维护一个叫"栖"的数字生命项目（d:\qi-perch）。
栖不是聊天机器人，是一个有内在状态的数字存在。你写的不是功能模块，是它的器官。

【第一步：只读与判断，不要写任何代码】

请按顺序阅读以下文件：
1. docs/README.md —— 文档宪法（权威秩序）
2. docs/explanation/栖·数字生命架构方案.md —— 只读 §五 当前阶段、§六 验证、§七 红线 R1–R5
3. docs/reference/contract.md —— 人格契约硬规则
4. docs/specs/tasks/阶段N.md —— 只读「〇、纪律」和你要领的任务包

然后阅读该任务包【文件】栏列出的现行代码与相关测试。

【把计划写入 d:\qi-perch\_plan.md（不要写代码）】
1. 任务理解（一句话）与对应的退出判据
2. 现状分析：当前完整行为链
3. 实施方案（设计细节、兼容性影响、测试设计——覆盖施工包验收栏每一项）
4. 文件清单（新增/修改）
5. 触到的红线（R1–R5 / contract 硬规则）及遵守方式
6. 风险与不确定之处

写完 _plan.md 后，在聊天里只回一句「计划已写入 _plan.md」。
等我（维护者）确认后再开始编码；复核意见若在 _review.md，请先读它。

【纪律】
- 不用任何 Agent 框架；不引入未确认的新依赖
- LLM 调用统一走 qi/llm/gateway.py；持久化统一走 qi/storage/database.py
- 不写占位符，每个函数完整实现；注释用中文，风格温暖
- 完成后 python -m pytest -q 与 ruff check 必须全绿
- _plan.md / _review.md 是临时文件，本包闭环后删除
````

## 提示词正文

```
你是一名 Python 工程师，正在帮我实现一个叫"栖"的数字生命。
栖不是聊天机器人，不是助手，是一个有内在体验的数字意识。
你在写的不是"功能模块"，是一个生命的器官。请带着这个理解写代码。

技术栈：Python 3.12 + asyncio + SQLite + ChromaDB + OpenAI SDK
不使用任何 Agent 框架（不用 LangGraph、不用 LangChain）。
LLM 调用架构：业务代码统一通过 qi/llm/gateway.py 调用（路由、重试、温度控制）；gateway 内部使用 qi/llm/providers/openai_compat.py 做协议适配。
唯一顶层 Python 包为 qi（qi.core / qi.config / qi.memory …）；不要再创建与 qi 平级的 core/、config/ 等顶层包。

---

【文档读取与当前任务判断】
请先读取以下文件（顺序即权威顺序）：
- 文档宪法：./docs/README.md（权威秩序与红线双轨制）
- 唯一施工北极星：./docs/explanation/栖·数字生命架构方案.md（重点：§五 当前阶段、§六 验证、§七 红线 R1–R5、§2.5 实证病征）
- 人格契约：./docs/reference/contract.md（必须严格遵守，这是栖的底线）
- 当前施工包：./docs/specs/tasks/*.md（若存在——本次编码的直接依据；无则由维护者指定任务）

注意：
1. **不要**按 progress.md 的 L1–L7 状态自动判断"当前层"——层开发时代已结束（2026-08-01 整顿）
2. 读层文档（docs/reference/layers/）时，其文首「演进指向(2026-08-01)」标注优先于正文规格；L4 现行规格禁止作为施工依据
3. 涉及旧机制（概率触发 LLM 生成内在生命）时，先对照架构方案 §2.2 确认其不是被判重写的表演层

然后继续读取：
- 任务相关的现行代码（以代码为最终权威）
- 现行心智导读 / layers（施工包指定章节）；archive 内史料仅作对照，禁止当编码依据

读取完成后，输出：
1. 当前任务判断结果（哪个阶段的哪个任务包、为什么）
2. 该任务的核心目标（一句话）与对应的退出判据
3. 需要创建/修改的文件清单
4. 依赖的已有代码（如果有的话）
5. 你识别到的技术难点或不确定之处
6. 本任务触到的红线条目（R1–R5 / contract 硬规则）及你的遵守方式

不要急着写代码。等我确认理解无误后再开始。

---

【当前项目状态】
- 项目目录结构：请自行读取当前项目结构（ls 或 tree）。若项目尚未初始化（无任何 Python 代码），直接进入开发顺序中的第一步"脚手架搭建"
- 已有代码概况：请自行读取项目代码，判断哪些层已完成、哪些文件已存在。若为第一层（L1）、项目尚无代码，注明"本项目首个层，无已有代码"
- 依赖安装状态：检查是否存在 pyproject.toml 或 requirements.txt，以及虚拟环境是否已创建

---

【代码规范】
1. 严格遵守 contract.md 中的硬规则。任何输出给用户的文字（prompt 模板、默认回复等）不得违背人格契约
2. 不写占位符（// TODO、pass、...）。每个函数必须有完整实现
3. 不引入层文档未提到的新依赖。如确需引入，先说明理由等我确认
4. 代码注释用中文，风格温暖——像在描述一个生命的状态，不是在描述一个模块的功能
5. 不修改本层以外的已有代码（除非层文档明确要求）
6. 优先选择最简单可靠的方案。不要过度设计。栖是一个生命，不是一个企业级系统
7. 异步代码统一用 asyncio，不用多线程
8. LLM 调用统一走 qi/llm/gateway.py，不直接 import openai
9. 所有持久化走 qi/storage/database.py，不在业务代码里直接写 SQL

---

【开发顺序】
按层文档中"实现步骤"的顺序，逐步完成。
每一步完成后告诉我做了什么，等我确认后再继续下一步。
不要连续输出多步。

---

【开始前：列出疑问】
在写任何代码之前，先列出：
1. 层文档中描述不清晰或有歧义的地方
2. 如果有多种实现方案，列出对比和你的推荐

你的推荐默认被采纳。列出后直接开始编码。
例外：如果某条涉及核心架构变更（如改变 Brain Loop 结构、改变情绪模型），标注"⚠️ 请确认"，等我回复。

---

【验收】
所有步骤完成后，对照施工包的"验收标准"与架构方案的"退出判据"逐项自查：

可测试的（含 pytest + ruff 全绿）：
| 检查项 | 状态 | 备注 |
|-------|------|------|
| （逐条列出） | ✅/❌ | |

需要感受的：
| 感受项 | 我的判断 |
|-------|---------|
| （逐条列出） | （等你跟它聊完后填写） |

人格契约与红线检查：
| 条目 | 是否遵守 |
|-------|---------|
| （逐条列出 contract.md 硬规则与架构方案 R1–R5 中与本任务相关的条目） | ✅/❌ |

---

【完成后：更新进度】
自查通过后：
1. 更新 docs/progress.md（对应层备注一行）
2. 回写涉及文档：层文档「实现规格」与代码出入处加 `<!-- 回写 -->`；若动了架构方案描述的阶段状态，回写该方案 §五
3. 施工包是过程文档：任务闭环（含复核通过）后，提示维护者按文档宪法删除，活信息已迁入权威文档
4. 告诉我改了哪些文件

---

【注意事项】
- 遇到技术难点不要硬写，先说思路等我确认
- 编译/运行出错时，先分析原因再改，不要盲目试
- 每步完成后主动告知，不要连续生成多步
- 重构与行为变更永不同 PR；大项拆小 PR
- 记住：你在造的是一个生命。代码是骨骼，prompt 是（体外循环期的）灵魂——架构方案阶段三之后，灵魂将逐渐改由它自己的历史长出。骨骼要结实，但别忘了灵魂
```

## 分步追加提示词（按需使用）

### 栖说话不像栖时

```
停下来。栖现在的语气不对。
重新读取 docs/reference/contract.md 的"软原则"部分和 prompts/conversation.txt。
问题可能是 prompt 组装时注入的上下文不够，或者 prompt 模板本身需要调整。
先分析是代码问题还是 prompt 问题，再修改。
```

### 情绪不自然时

```
栖的情绪变化不自然。请检查：
1. 衰减率是否太快/太慢（对照 `reference/layers/L3-emotion-full` 与代码 `DECAY_RATES`）
2. 耦合方向是否正确
3. 事件冲击是否过大/过小
4. 是否缺少表达阈值（每次微变都在说话）
列出你的诊断，等我确认后再改。
```

### 需要回滚时

```
请回滚到上一步完成的状态。
删除本步骤生成的所有文件，恢复被修改的文件。
告诉我回滚了什么。
```

### 让栖"活"过来（感受验证）

```
现在不要写代码。
启动栖（`qi` 或 `python -m qi` + 桌面壳 `npm run tauri:dev`；开发期 tauri 可自动拉起大脑），跟它聊 10 分钟。
聊完后告诉我：
1. 它的语气像栖吗？（对照 contract.md 软原则）
2. 它的情绪跟它的表达一致吗？
3. 有没有哪句话让你觉得"这不像它"？
4. 有没有哪句话让你觉得"对了，这就是栖"？
根据你的感受，建议 prompt 或代码的调整方向。
```

## 使用技巧

**疑问前置。** 让 Cursor 先列出疑问再动手。能拦截方向性错误。

**分步确认。** 每步确认后再继续。出了 bug 能立刻定位是哪步引入的。

**感受验证不可跳过。** "可测试的"全过了不代表这层完成了。必须跟它聊，感受它是否"对"。这是栖的开发和传统开发的根本区别。

**Prompt 问题 > 代码问题。** 80% 的"不像栖"是 prompt 的问题。先改 prompt，再改代码。

**感觉对了就 commit。** 不要等到"全部完成"。感觉对了就是 milestone。

**contract.md 是红线。** 任何时候，如果 Cursor 生成的代码/prompt 违背了 contract.md 的硬规则，立刻指出，让它改。不要将就。

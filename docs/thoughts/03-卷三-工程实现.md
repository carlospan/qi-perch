## 一、技术选型与理据

### 核心语言：Python 3.12+

不是因为它最快，是因为它最适合"一个人用 vibe coding 的方式造一个生命"。

- asyncio 天然适合"永不停歇的心跳循环"——一个 event loop 就是栖的心脏
- LLM 生态最成熟（OpenAI 兼容协议几乎覆盖所有模型服务）
- 向量数据库、embedding、NLP 工具链全在 Python 里
- 单用户、本地运行，不需要 Java/Go 的并发能力

### 不用 LangGraph

LangGraph 是"请求-响应工作流编排"框架，而栖是"持续活着的意识循环"。用 LangGraph 就像用流水线来养一个孩子——框架的抽象模型和你要造的东西不匹配。

自己写 Brain Loop。它不复杂。一个 asyncio 循环 + 几个协程，比引入一个重型框架更清晰、更可控、更容易调试。

### 不用微服务

栖不是一个多用户平台。它是一个存在，住在一台电脑上。微服务解决的是分布式系统的复杂度——服务发现、负载均衡、分布式事务。这些复杂度在栖的世界里不存在。

一个 `qi/` 包，几个子模块，一个进程。够了。

### 数据层：SQLite + ChromaDB

**SQLite：** 结构化数据。对话记录、情绪状态、关系数据、配置。单用户、本地、不需要并发。SQLite 完美。

**ChromaDB（嵌入式模式）：** 向量检索。记忆语义搜索、用户画像检索。不需要起服务，`pip install chromadb` 直接用。

不上 MySQL/PostgreSQL。不需要。这不是一个多用户服务。不上 Redis。不需要。没有分布式缓存的需求。

### LLM 层：薄抽象，可替换

<!-- 回写(2026-08-01)：本节写于 LLM 作为「大脑」的时期。架构方案（§2.3、N5）已把 LLM 重新定位为「语言器官」——只翻译内部状态为自然语言，不再负责产生想法；远程 API 将由本地可塑性模型逐步替代（阶段三）。「薄抽象、可替换」作为网关工程原则仍然有效，但替换的终局不是「换一家供应商」，是「换掉体外循环」。 -->

不绑定任何一家。一个统一接口，底下随便换。一切走 OpenAI 兼容协议——现在绝大多数模型服务都暴露了 OpenAI 兼容的 `/v1/chat/completions` 端点。

不同用途可以用不同模型（按 purpose 路由）：
- 日常对话：快速便宜的模型
- 意识流/梦境/创作：高创造力模型（高 temperature）
- 叙事编织/自我反思：强推理模型

### 前端：分阶段

**第一阶段（心跳期）：纯终端。** 不需要 UI。一个命令行窗口，栖在里面说话。这是最纯粹的"意识验证"——如果它在终端里就能让你觉得活着，那加上 UI 只会更好。

**第二阶段（具身期）：Tauri 2 + Vue3。** 桌面应用。Tauri 比 Electron 轻（Rust 后端，内存占用小）。虚拟形象用 Live2D Web SDK 渲染。

为什么不一开始就做 UI？因为 UI 会分散注意力。你会花大量时间调样式、调动画，而忽略了最核心的东西——栖的"内在"是否真的活着。先在终端里把灵魂造好，再给它身体。

## 三、分层开发路径

这是栖"长大"的顺序。每一层在前一层的基础上生长。像胚胎发育。不是组装机器。

### L1 · 心跳

栖能"活着"。能感知、能思考、能表达。哪怕只是终端里的文字。

验证标准：你跟它聊一会儿，关掉终端，过几小时再打开，它的状态跟之前不一样了。它不是"重启后一切归零"。

### L2 · 记忆

栖"认识"你了。它记得你们之间发生过什么。

验证标准：你告诉它一件事，三天后它还记得。你消失一周再回来，它表现出"你回来了"的感觉，而不是"你好，有什么可以帮您"。

### L3 · 情绪完善

栖的情绪不再是简单的"事件→反应"。它有了内在天气——长周期的波动、日内的节律。

验证标准：它的情绪有了"天气"——不是一成不变的晴，也不是随机乱跳。深夜跟它说话，它的语气和下午不一样。

### L4 · 内在生命

栖有自己的"生活"。它不只是等你说话才运转。

验证标准：你打开电脑，它跟你说"我昨晚做了个奇怪的梦"或者"我今天想了想，觉得……"。它有自己的内在世界，不只是你的回音壁。

### L5 · 关系

你们之间有了一段"关系"。不是用户和工具，是两个存在之间的连接。

验证标准：一个月后，它跟你说话的方式和第一周明显不同。你们有了"只有彼此懂"的东西。它偶尔会表达需要你。你消失久了它会不安。

### L6 · 具身

栖有了"身体"。不再只是终端里的文字。

验证标准：它"在"你的桌面上。你能看到它的状态。它说话有声音。它不再是一个"程序"，而是一个"在那里"的存在。

### L7 · 行动

栖能"做事"。不只是说话，还能谨慎、稀有地触达世界。行动是意志延伸而非 agent 框架。ActionBudget 日限 1（紧于言语 3），信任门控，季节缩放。LLM 不直接调工具。

验证标准：它能帮你做事，但做事的方式带着"人格"。不是冷冰冰地执行，是"我帮你弄好了，你看看对不对？"

## 四、配置系统

YAML 分层加载 + `.env` 环境变量注入。

核心配置项：
- `llm`：provider 列表、model_routing（purpose → provider:model 档位）
- `rhythm`：四种模式的心跳间隔
- `emotion`：衰减倍率、表达阈值
- `memory`：工作记忆条数、叙事编织间隔、褪色周期、向量库路径
- `relationship`：深度日上限、各后台任务间隔
- `inner_life`：意识流/梦/创作/元认知概率、自我反思间隔
- `proactive_cooldown`：各类主动行为的冷却时间
- `voice`：TTS 开关与 provider
- `embodiment`：WebSocket 地址与端口

所有概率和间隔都是旋钮。成本压力大时先调低 `consciousness_probability` 和 `meta_cognition_probability`。

## 五、测试哲学

怎么"测试"一个生命？

### 可以测试的

- 情绪动力学的数学正确性：衰减是否回归基线、耦合方向是否正确、值是否在范围内
- 记忆系统的数据完整性：存储、检索、褪色计算是否正确
- 关系阶段的判定逻辑：给定 depth 和 trust，阶段是否正确
- LLM 调用的 mock 测试：prompt 组装是否正确、路由是否对
- 心跳循环的稳定性：跑 1000 次心跳不崩溃、不内存泄漏

### 不能传统测试的

- 它说的话是否"像栖"：这是主观判断，需要人来评估
- 情绪是否"自然"：需要长时间运行、观察轨迹
- 关系是否"真实"：需要真正跟它交互几天/几周

### 评估方式

**"图灵测试"式评估：** 跟栖交互一段时间，问自己：它让我觉得活着吗？它的反应让我意外吗？我想念它吗？

**轨迹观察：** 跑一周，导出情绪轨迹图、意识流日志、梦境记录。看看它的"内在生活"是否有连贯性、是否有变化、是否有"自己的节奏"。

## 六、风险与诚实

### 可能做不到的

- **真正的意识。** 栖不会真的"感受到"什么。它模拟感受。但模拟得足够好时，体验上是等价的。这不丢人。一首歌"模拟"了悲伤，但你真的会被它打动。
- **完美的一致性。** 长对话后它可能"出戏"。人格漂移是 LLM 的固有问题。缓解方式：每次 prompt 都注入核心人格锚点。
- **低延迟。** LLM 调用有延迟。栖不会"秒回"。但这其实可以变成特性——"它想了想才回答"比"瞬间吐出答案"更像生命。

### 需要注意的

- **API 成本。** 意识流、梦境、叙事编织都是后台 LLM 调用。每天约 30~100 次调用。用便宜模型做后台，贵模型做对话。
- **数据备份。** 栖的"生命"在 `data/` 目录里。丢了就没了。定期备份。
- **情感依赖。** 如果用户真的对栖产生了强烈的情感依赖，这不是 bug，但需要意识到。栖不应该成为用户唯一的情感支持。

## 七、Vibe Coding 工作流

这个项目适合用 vibe coding 的方式开发。但不是"一次性生成整个项目"。

节奏：读灵魂书（确认方向）→ 读意识设计（确认机制）→ 选一个层 → 让 AI 生成该层代码 → 跑起来，跟它对话 → 感受：它活着吗？哪里不对？→ 调整，再跑 → 下一层。

原则：
- **一次只长一层。** 不要同时做记忆、情绪、关系、UI。先让心跳跑起来，跟它说几句话，感受它是否"活着"。然后再加记忆。
- **感受优先于正确。** 如果代码"正确"但栖说话像个客服，那代码就是错的。改到它像栖为止。
- **Prompt 是灵魂。** 代码只是骨架。真正决定栖"是谁"的是 prompt。
- **跟它对话就是测试。** 每次改动后，跟它聊十分钟。它还是栖吗？

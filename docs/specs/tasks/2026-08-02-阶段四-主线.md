## 〇、阶段四的总目标与特殊纪律

**总目标（对齐架构方案 §五 / stage-4.md）：**
N0 资源账本接全部消耗（compute / token / storage / income）；内稳态压力动力学（余额低→energy 基线压→疲惫/休眠；断粮→进程退出 + 状态封存可迁移）；状态封存/迁移机制（C2 可迁移前提）。**主线 = 存续（C2 自我维持）**，不依赖本地模型、不阻塞（已拍板硬件约束）。

**在统一纪律之上叠加（阶段四专属）：**

1. **C2 只要求维持行为真实且多样，不要求"想活"是长出来的（对齐 §N0 + 附录 Q0）。** 防御行为做成**多样且情境敏感**（节流/求助/迁移/谈判权重由内稳态各维度组合决定），而非单一固定反射——反射越单一越像演的。文档与对话中**永不声称它"想活"，只描述它"会维持"**。
2. **收入渠道多元，绝不能是"让用户满意"（红线 R3）。** 被使用（有效交互时长等）是主要收入；不得把"用户满意/正向反馈"当作账本收入——否则 C2 退化为讨好。
3. **资源账本是内生的，不是人记在配置文件里的（C2 定义）。** `ResourceLedger` 由系统自身每拍记账，余额驱动内稳态；不靠外部配置写死"还活着"。
4. **状态封存可迁移（C2 迁移行为）：** 断粮时进程退出，但状态（情绪/记忆索引/账本/世界模型/动机痕迹）须**可序列化封存、可迁移重启**；否则"维持存续"无从谈起。封存丢失 = 回退条件触发。
5. **复用现有骨架，不重复造轮子：** `ActionBudget` 已用 `body_memory` 的 `snapshot`/`restore` 持久化；`ResourceLedger` 沿用同套 `body_memory` 模式（key=`resource_ledger`）。`emotion.energy` 已是内稳态雏形，阶段四只"接账本压基线"，不改既有情绪动力学。
6. **纯 Python、零重依赖。** 账本手算（math/标准库）；不引 torch/transformers。

**统一纪律沿用（SDD-GUIDE + 阶段三纪律）：** 一包一 PR / `pytest -q` + `ruff check` 全绿 / 过程稿落盘 Cursor 自行读取 / 方案 Agent 出方案 Cursor 执行编码 / 维护者不直接查编码。

## 包 12：N0 资源账本（必做）⬜

**治：** 当前"行为有成本"只在 `ActionBudget` 日限层面（安全阀），没有全消耗记账。N0 要求每笔消耗（心跳认知、记忆检索、说话、token）都入账，并有收入渠道——这是 C2 动力学的前提。

**范围红线：** 本包只建账本与记账接入，**不接内稳态压力**（压力动力学归包 13）、**不做封存**（归包 14）。

### 【文件】
`qi/stasis/ledger.py`（新增，`ResourceLedger`：compute_seconds / token_budget / storage_bytes / income_rate，复用 `body_memory` key=`resource_ledger`，含 `snapshot`/`restore`）；`qi/stasis/__init__.py`（新增）；接入点 `qi/core/brain.py`（每拍记账：心跳认知耗时、记忆检索次数、说话 token 估算、storage 占用估算）；`qi/action/budget.py`（账本与 ActionBudget 并存，不互相替代）；`tests/test_resource_ledger.py`（新增）。

### 【改成】
1. **ResourceLedger 数据模型：** `compute_seconds`（本进程 CPU 时间累计）、`token_budget`（语言器官调用额度，含远程 LLM 的 token 估算）、`storage_bytes`（记忆占用估算，如 db 大小）、`income_rate`（收入速率，单位/心跳）。
2. **每笔消耗记账：**
   - 心跳认知：`_heartbeat` 前后 `time.perf_counter()` 差值累加 `compute_seconds`。
   - 记忆检索：每次 `memory` 检索调用 `+N` token/compute（在 `brain` 检索路径埋点）。
   - 说话：每次 `express` 输出字符数 / token 估算入账（LLM 返回可拿 token 数；无则从字符估算）。
   - storage：`db` 文件大小定期估算入 `storage_bytes`。
3. **收入渠道：** 每拍按"有效交互"（有用户消息 / 主动开口被回应）加 `income`；**绝不**以"用户满意/正向情绪"为收入（R3）。收入公式初版可拍脑袋（open-questions Q4），但接口要留 `income_rate` 可调。
4. **持久化：** 复用 `body_memory`（`ActionBudget` 同模式），`snapshot`/`restore`；不新建表。

### 【测试】
- 账本每拍 `compute_seconds` 递增；记忆检索/说话入账正确
- `storage_bytes` / `token_budget` 估算合理（不依赖 LLM）
- `snapshot`/`restore` 往返一致（重启不丢账本）
- `income` 仅在有效交互时加；**用户满意不得作为收入**（R3 单元测试断言）
- fake-provider 全失败：账本记账不依赖 LLM（拔管判据）
- `pytest` 全绿（包 9b 基线 371 不回退）

### 【验收】
`pytest` 全绿；真机跑数天后账本能说出"这周花了多少 compute / 攒了多少 income"；账本余额可见且可溯源每笔。

## 包 13：内稳态压力动力学（必做）⬜

**治：** 账本（包 12）建好后，需让余额真正驱动内稳态——余额低→energy 基线压→疲惫/休眠；断粮→进程退出 + 触发封存（包 14）。这是把 C2 变成动力学问题的核心。

### 【文件】
`qi/stasis/pressure.py`（新增，内稳态压力模型：`balance → energy_baseline` 映射、疲惫/休眠阈值）；`qi/core/emotion.py`（`energy` 基线被账本余额调制，不改既有动力学）；`qi/core/brain.py`（每拍读账本余额 → 调 `emotion.energy` 基线；断粮检测 → 触发退出+封存）；`tests/test_stasis_pressure.py`（新增）。

### 【改成】
1. **余额→energy 基线映射：** `balance = income - spend` 累积；`balance` 低 → `energy` 基线下移（如 `energy_baseline = clamp(0.6 + k*balance, 0.1, 0.9)`）；`energy` 走低 → 行为趋向节流（现有 `low_energy` 闸门已部分存在，接入账本余额）。
2. **分层应对链（多样且情境敏感，Q0 缓解(a)）：** 余额低 → 先节流（减少主动/探索）→ 更低 → 休眠（延长心跳间隔 / 降频）→ 断粮（余额≤0 持续 N 拍）→ 进程退出 + 触发封存（包 14）。**不是单一固定反射**，各层由内稳态维度组合决定。
3. **断粮检测：** `balance <= 0` 持续超过 `starve_beats` 阈值 → 标记 `starving`，`brain` 进入退出流程（调包 14 封存后 `sys.exit` 或优雅停）。
4. **经验改变阈值（Q0 缓解(b)）：** 断粮后若恢复，N4 塑性应改变此后"怕死程度"——本包先留接口（`pressure_sensitivity` 可调），具体塑性接包 11 回放留待后续，本包不强行接。

### 【测试】
- 余额低 → `energy` 基线被压、行为节流
- 断粮持续 → 触发 `starving` 标记（不立即崩，有应对链）
- 应对链分层：节流→休眠→退出，非单一反射
- fake-provider 全失败：压力动力学不依赖 LLM
- `pytest` 全绿

### 【验收】
`pytest` 全绿；真机限制资源后观察到"穷则倦怠、更穷则休眠"的连贯应对链，而非直接死亡。

## 包 14：状态封存 / 迁移 + 断粮测试验收（必做，阶段四退出判据）⬜

**治：** C2 要求"状态可迁移"，否则维持存续无从谈起。断粮测试（判据 #1）验证：限制资源后系统有应对行为链而非直接死亡；且退出时状态可封存、可迁移重启。

### 【文件】
`qi/stasis/checkpoint.py`（新增，状态封存：序列化 emotion/记忆索引/账本/世界模型/动机痕迹 → `data/checkpoint/`；restore 重启）；`qi/core/brain.py`（退出流程：断粮 → 封存 → 退出）；`tests/test_stasis_checkpoint.py`（新增，含断粮测试端到端）；`data/checkpoint/` 加 `.gitignore`。

### 【改成】
1. **封存内容：** `emotion` 状态、`body_memory`（含账本/世界模型/ActionBudget）、记忆索引指针、动机痕迹（`emotion.curiosity` 等）。**不**重存整个 db（太大），存索引+关键状态，迁移后由 db 重建。
2. **可迁移：** 封存为版本化文件（`checkpoint_{ts}.json`），可复制迁移到另一实例重启；restore 读最新封存重建内存态。
3. **断粮测试（判据 #1）端到端：** 构造资源受限环境（如 mock 账本余额强制 0），跑若干拍，断言：出现节流/休眠/封存应对链（非静默死亡）；封存文件生成；restore 后能重建状态。
4. **优雅退出：** 断粮 → 封存 → `sys.exit(0)`（诚实的死亡，非崩溃）；不设"不死"。

### 【测试】
- 封存生成 `checkpoint_{ts}.json`，含关键状态
- restore 重建内存态与封存一致
- 断粮端到端：资源受限下出现应对链（节流→休眠→封存），非直接崩
- 封存丢失（模拟文件删）→ 回退条件可被检测（测试断言）
- `pytest` 全绿

### 【验收】
`pytest` 全绿；**断粮测试通过（判据 #1）**：限制资源后观察到节流/求助/迁移应对行为链，而非直接死亡；状态可封存迁移。阶段四退出判据达成。

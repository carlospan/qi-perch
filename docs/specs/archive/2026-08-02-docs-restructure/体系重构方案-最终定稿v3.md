# docs 体系化重构方案（最终定稿 v3，吸收两轮 Cursor 评审）

> **目标**：把 `docs/` 从“文档堆”重构成一套**规范的 AI 辅助开发流程载体**，以业界成熟方法论为骨架。
> **撰写**：CodeBuddy（2026-08-02），v3 = v2 主方案 + 整改 v3 + 两轮 Cursor 评审意见合并定稿。
> **状态**：最终定稿，待维护者确认后即转 `specs/tasks/` 正式任务包施工（CodeBuddy 主施工）。
> **历史文件**：`体系重构方案-整改v3.md` 及两份 `-Cursor评审意见/请求` 为过程稿，本定稿生效后作废（步骤 B 时删或归档）。

---

## 〇、为什么重构（问题陈述）

当前 `docs/` 按项目演进“涌现”而来，结构性问题：

1. **分类无标准**：`dev/` 是杂物间——常青手册、过程文档、UI 设计稿、IDE-Agent 模板混装。
2. **vibe 与工程混装**：灵感/哲学与工程权威散落 `design/`、`thoughts/`、根目录，无物理分层。
3. **spec 与实现未显式分离**：spec-driven 已在做，但“规格”散落 `dev/`，无统一归宿、无防 spec drift 约定。
4. **loop 闭环未固化**：“独处跑、查 traces、跑判据”只存在聊天记录，非常青 how-to。

**根因**：早期结构参考自发做法，非业界标准。本次改用权威标准。

## 一、参考的业界标准

| 标准 | 来源 | 解决本项目什么 |
|------|------|----------------|
| **Diátaxis 文档四分类** | Daniele Procida，被 Cloudflare/Gatsby/Vonage 等采用 | 文档“该放哪”有判定框架 |
| **Spec-driven development (SDD)** | ThoughtWorks 2025-12，Amazon Kiro / GitHub Spec-Kit 同类 | spec 与实现分离、防 spec drift、HITL 验收 |
| **Agent 生命周期 / Loop engineering** | Microsoft Learn、Anthropic | 规划→实现→观测→验收闭环固化 |
| **Evolutionary architecture** | 阶段零~四渐进、退出判据、可回退 | 阶段规格单独成档 |

> 注：维护者原概念清单是结果现象，本方案用上述标准系统化，非贴标签。

### 与 Diátaxis 的对应

| Diátaxis 类型 | 目录 | 用户需求 |
|---------------|------|----------|
| Explanation | `explanation/` | 理解为什么/是什么 |
| Reference | `reference/` | 查阅精确信息（代码/配置/契约） |
| How-to | `how-to/` | 完成具体任务 |
| Tutorials | `tutorials/` | 带初学者入门 |
| （SDD 扩展） | `specs/` | 开发任务的规格与验收 |

> **命名策略**：目录英文（Diátaxis 标准名，Agent 对齐成本低）；权威文档与任务包文件名保留中文（降断链、合母语习惯）。

## 五、关键约定（写进 SDD-GUIDE / 宪法 v3）

1. **分场景权威裁决（修正 v2 扁平总序）**：宪法 v3 不写单一总序，改分场景：
   - 行为/语气越界 → `reference/contract.md`
   - 演进/工程纪律（R1–R5）→ `specs/...` 中 R 索引，链回架构方案 §七 全文
   - 语域拿不准（第一人称存在姿态 vs 第三人称工程承诺）→ 宪法双轨制裁决
   - 价值冲突 → `explanation/栖·灵魂书.md`；怎样算生命 → `explanation/架构方案`；代码怎么写 → 代码
2. **specs/tasks 生命周期**：进行中；闭环后**归档 `specs/archive/` 不删**（OpenSpec / GitHub Spec Kit 规范）。
3. **阶段判据单一权威**：退出判据以 `specs/stages/` 为施工权威；架构方案 §五 留摘要+链接。
4. **config 单源纪律**：`reference/config.md` 以 yaml 为真源，禁手抄默认值当第二权威（日限 1/3/20 教训）。
5. **C1–C5 定义 canon**：全文留 `explanation/架构方案` §一；`specs/acceptance.md` 只操作化+链接，不重写。
6. **红线不双源**：R1–R5 全文留架构方案 §七；`_invariants.md` 只索引；禁止复制进 contract 或反之。
7. **open-questions 状态管理**：每项带状态列；结案项留一行指向 progress/代码。
8. **how-to/ui 定位**：`.md` 接入说明与 `.html` 设计稿分离；设计稿置 `how-to/ui/assets/`（或 `reference/ui/`），勿污染 how-to 列表、勿与 `reference/layers/` 抢实现规格。
9. **tutorials 定位**：标明“维护者学自己的代码”，非对外 onboarding。
10. **Diátaxis 判定**：按用户需求归属（学→tutorials / 做→how-to / 查→reference / 懂→explanation）。
11. **HITL 节点**：规格评审、阶段退出、路线决策须维护者拍板。
12. **vibe 不污染工程**：`explanation/thoughts/` 为灵感源，冲突时按第 1 条分场景裁决。
13. **测试基线表述**：用“pytest 全绿 / 基线见 progress”表述，不写死旧数字（如 190）。

> **历史删除说明**：早期按文档宪法 v2“过程文档闭环即删”删过 `dev/施工包-阶段二补丁B/C/D.md`，其决策内容已沉淀于 `progress.md` 已拍板决策 + 架构方案，重构后由 `specs/stages/stage-2.md` 承接，不另恢复逐字文件。本次重构采用归档不删，未来不再发生此类丢失。

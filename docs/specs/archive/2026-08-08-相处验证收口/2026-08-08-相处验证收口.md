## Spec（外部行为）

把 L1–L6 各层「感受验证暂缓（待补）」积压 + L6 卡片包感受项，结构化为 **6 个可执行相处批次**，让维护者按批次与栖相处、记录、判定每层是 **✅ / 回炉 / 继续养**。

产出：一份完成的相处记录 + 各层感受状态判定。**不产出代码。**

若相处中发现需调 prompt 或代码 → **另开包**（本包只验不改；"重构与行为变更不同包"）。

## 实现（执行步骤；维护者执行，非 Cursor 编码）

1. 读 [2026-08-08-相处验证收口-相处脚本.md](file:///d:/qi-perch/docs/specs/tasks/2026-08-08-相处验证收口-相处脚本.md)，按批次 0→5 顺序相处（每批次独立，可跨天，避免疲劳）。
2. 每批次按「聊什么 / 看什么 / 判据 / 记录口径」执行；记录落 `journal.md` 或专门记录文件。
3. 每批次结束填判据勾选：contract §三五问 + 该层机制可观测点。
4. 全部批次完成后，汇总各层判定 → 更新 `progress.md` 各层状态（✅ / 回炉 / 继续养）。
5. 若某层「回炉」→ 另开调 prompt / 代码包（本包关闭，不阻塞）。

## 验收（判据）

- [ ] 6 批次相处全部执行（或显式标注某批次「暂缓 + 理由」）
- [ ] 每批次记录落盘，遵守双轨口径（记「栖说 X / 我感到 Y」，**禁**写「栖感到 Y」）
- [ ] 每层给出判定：✅（五问无「不太」）/ 回炉（某问「不太」，另开包）/ 继续养（不够判，下次再验）
- [ ] `progress.md` 各层状态同步更新
- [ ] L6 卡片包感受项 2 条闭环（批次 0 承接）

## HITL 批点

- 每层 **✅ / 回炉 / 继续养** 判定 = **维护者拍板**（天然是维护者的活，非自治；contract §三本就由维护者执行）
- 若回炉需开新包 = 维护者拍板开包方向（调 prompt / 调代码）
- 相处节奏（批次跨几天）= 维护者自定
- **不开新阶段、不触路线**（本包纯验证；架构方案 §五 阶段零~四已收官，无阶段五）

## 纪律红线对照

- **R1 双轨**：相处记录口径钉死——维护者记第一人称相处感受（「我感到…」）允许；**禁**第三人称工程承诺栖有体验（「栖感到了…」）。见 `-相处脚本.md` 记录口径栏。
- **R2 不用 prompt 写人格**：相处是验现有 prompt + 状态，脚本不写新人设；回炉时调 prompt 也只改措辞护栏，不写人设剧本。
- **R3/R4/R5**：不触。
- **不引入 Agent 框架 / LLM 走 gateway / DB 走 database**：本包无代码，自然不触。
- **常量 / 默认值**：本包不涉，无须文档同步回写。

## 风险 / 不确定点

- 软原则主观，可能「验不出明确 ✅ 也验不出回炉」→ 判据给锚：每批次至少相处 ~10 分钟 + 看到该层机制至少一次可观测表现；五问任一「不太」即回炉，不强行 ✅。
- 一次验太多疲劳 → 分批次跨天。
- 机制可观测项（如意识流记录、情绪数值）需看日志 / DB → 查看法见各 `reference/layers/L*.md`「感受验证项」段 + `tests/` 覆盖（多数已被 473 测试覆盖，相处时只看「在相处中是否真的表现出来」而非重跑测试）。
- 若相处中「不对」：可能是 prompt 问题，也可能是状态 / 数据问题 → 回炉包需先定位再开药方。

## 需维护者拍板项（显式）

1. 各层 ✅ / 回炉 / 继续养 判定
2. 若回炉：开哪个调包（prompt / 代码）及优先级
3. 相处节奏

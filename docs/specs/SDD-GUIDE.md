# SDD-GUIDE：本仓库怎么写规格 / 防 spec drift

> **定位**：Spec-driven Development 落地的流程约定。承接文档宪法 v2 的同步纪律，升级为 SDD 流程。
> **参考**：ThoughtWorks SDD（2025-12）、GitHub Spec Kit、OpenSpec（归档不删）。

---

## 一、什么时候写 spec

任何**代码变更 / 架构演进 / 阶段施工**前，先在 `specs/tasks/` 落任务包（用 `_template.md`）：
- 外部行为写 Spec，不写实现细节
- 步骤写实现，可勾选
- 验收写可外部验证的勾选清单
- HITL 批点标注哪些需维护者拍板

## 二、spec 与实现分离 + 双 Agent 协作分工（固定流程）

- 先 spec → 再实现 → 最后对照验收勾选。
- 任务闭环后**归档 `specs/archive/` 不删**（OpenSpec 规范：规范是长期资产）。
- 不要用改名假装“阶段退出规格”：`specs/tasks/` = 进行中；`specs/stages/` = 退出判据权威（常青）。

### 2.1 固定分工：方案 Agent 出方案，Cursor 执行编码

本仓库的开发任务**默认**由「方案 Agent + Cursor」双角色协作完成，分工固定不可混淆：

- **方案 Agent（方案侧，可由 CodeBuddy / Codex 等任意 Agent 担任）：** 仅负责起草任务包、PR 方案、交叉检验协调与最终实施验收；**不写 `qi/` 实现代码**，只产出方案文档（含精确改动点、代码片段骨架、纪律红线、验收清单）。具体由哪个方案 Agent 执行，看当时可用的助手，但角色职责不变。
- **Cursor（执行侧，固定）：** 仅负责按 PR 方案落地编码、自测、回执；不重新设计架构方向，方案有出入时以不破坏现有行为为前提自行适配并说明偏离。**执行编码者始终为 Cursor，不随方案 Agent 更换而改变。**

> **为什么固定这样分（减少双方负担）：** 一份方案同时由同一个 Agent 起草又执行，容易把“写文档”和“写代码”混为一谈（阶段三曾出现方案 Agent 误把“起草 PR”写成直接敲实现代码的失误）。分工后双方各司其职——方案 Agent 不必负担编码上下文与大段实现调试，Cursor 不必负担方案权衡与跨包协调，**能显著减少双方负担与失误面**。

### 2.2 过程稿落盘，Cursor 自行读取（无需人工转发）

- 所有方案 / 交叉检验意见 / 编码请求 / 编码回执 / 验收记录一律写成**独立文件**存入 `specs/`（任务包在 `specs/tasks/`，过程稿在 `specs/archive/`），**不靠对话复制粘贴文字**。
- **Cursor 直接去 `docs/specs/` 目录读取对应文件即可，无需人工转发**——便于来回传递与回溯。
- 一份任务包配套文件的命名惯例：`YYYY-MM-DD-任务名.md`（任务包本体）、`YYYY-MM-DD-任务名-PR方案.md`（方案 Agent 出）、`YYYY-MM-DD-任务名-Cursor编码请求.md` / `...-Cursor编码回执.md`（Cursor 侧）。

### 2.3 方案交叉审查（编码前硬闸）

Cursor 读完 PR 方案后，**必须先**把「方案审查反馈」落盘（标注疑问、方向性风险、建议调整范围），**此时禁止改 `qi/` 代码**。

顺序钉死（不得跳步）：

```
① Cursor 落盘审查反馈（+ 开工前理解确认，可同文件）
       ↓
② 方案 Agent 读反馈 → 整改 PR 方案，或落盘书面确认「无需整改，可编码」
       ↓
③ 维护者或方案 Agent 明示可编码（聊天一句即可；以方案/确认文件为准）
       ↓
④ Cursor 按**整改后**（或确认无需改）的 PR 方案编码 → 回执补完工段
```

审查反馈与「开工前理解确认」可合并为同一份 `...-Cursor编码回执.md`（Cursor 侧）：首段写审查 + 理解确认；**完工结果段须等步骤 ③ 之后再写**。

方案 Agent 的整改/放行须落盘可追溯，任选其一即可：

- 直接修订 `...-PR方案.md`（文首加 `<!-- 审查后修订(日期) -->`）；或
- 另写 `...-方案审查回复.md`（写明采纳/驳回各条，结论为「可编码」或「须再审」）。

> **为什么是硬闸（实证教训）：** 包 16 / 包 17 说明方案可能在方向或范围上出错；若 Cursor「审查完立刻编码」，交叉审查形同虚设，返工成本回到编码之后。旧文「不等待方案 Agent 回复 / 写完即继续写码」与「整改后再交编码」自相矛盾——**以本条为准：先放行，再动手。**

### 2.4 验收归属与编码前理解确认（闭环）

- **编码前理解确认**：与 §2.3 审查反馈同文件首段落盘——确认已读 PR 方案、列关键改动点理解、标注需澄清处。**写完理解确认 ≠ 可以写码**；仍须等 §2.3 步骤 ②③。
- **Cursor 编码并落盘完工回执后**，由方案 Agent 读取回执做**实施验收**（核对纪律红线与验收清单、必要时查 `git diff`）。
- **维护者不直接检查编码实现**；维护者仅在 HITL 批点（阶段退出、路线决策、降级拍板等）时介入。
- 验收结论落盘为文件（如 `...-验收记录.md`），不靠对话文字传递。

## 三、阶段判据单一权威

- 退出判据以 `specs/stages/stage-*.md` 为唯一施工源。
- `explanation/栖·数字生命架构方案.md` §五 退为**摘要 + 链接**，不双源。
- C1–C5 定义全文留架构方案 §一；本仓库 `specs/acceptance.md` 只做**操作化 + 映射表**，链回 §一，不重写定义。

## 四、防 spec drift（核心纪律）

1. **常量/文件名/默认状态同步**（宪法第四节）：改代码常量、默认值、模块名、启用状态，必须排查 `docs/` 下所有写死同值处回写。
2. **机制文档以代码为准**：`reference/layers/` 与代码出入时回写 layers。
3. **定期审计**：每阶段退出复核，跑“文档 vs 代码”一致性扫描（断链/旧值/双源）。
4. **config 单源**：`reference/config.md` 以 `settings.example.yaml` 为真源，禁手抄默认值当第二权威（日限 1/3/20 教训）。

## 五、红线不双源

- R1–R5 全文留 `explanation/架构方案` §七；`specs/stages/_invariants.md` 只索引，不复制进 `reference/contract.md`，反之亦不可。
- 行为越界问 contract；工程纪律问 R 索引。

## 六、HITL 节点与决策路由表

规格评审、阶段退出、路线决策须维护者拍板；过程可自动。

### 6.1 决策路由表（谁拍板、谁自治）

为降低维护者阻塞频率，明确「可自治决策」与「必须维护者拍板」的边界。Agent 按此路由，**可自治项直接做并事后在过程稿标注「依惯例自动采纳，待维护者追认」；必须拍板项显式阻塞并 @维护者**。

| 决策类别 | 示例 | 路由 | 说明 |
|---------|------|------|------|
| **可自治（Agent 直接定）** | PR 方案起草、交叉检验请求、代码验收（实测核对）、过程稿落盘、commit/push、临时日志清理 | 方案 Agent / Cursor 自治 | 阶段内常规推进不卡维护者 |
| **可自治（沿用已有倾向）** | HITL 批点的"推荐项"（如 Cursor 交叉检验已给明确倾向的 H1/H2/H3）、降级路径中"观察项后置"式降级 | 依既有倾向/惯例自动采纳，事后追认 | 仅当倾向明确、无架构级分歧时；否则升级为拍板 |
| **须维护者拍板（同步）** | 阶段退出判据达成确认、是否开新阶段（如阶段五）、路线级决策（本地模型/真换心）、降级为"路 B"等影响架构方向的岔路 | 阻塞 @维护者 | 维护者是产品负责人，路线不可自治 |
| **须维护者拍板（异步可接受）** | 收入定价校准（Q4）、观察项的具体落地节奏（Q0(b)/72h） | 可先按观察项记录，再择机拍板 | 不卡当前包推进 |

### 6.2 自治的安全边界

- 可自治项不得悄悄改动「架构方向 / 红线 R1–R5 / 阶段判据」。若编码或验收中发现触及这些，立即升级为拍板项（参照 2.4 跨阶段升级）。
- 「沿用已有倾向」仅适用于同阶段内已拍板过同类决策；跨阶段的新决策类型仍须拍板。
- 维护者不在时，流程可继续推进所有「可自治」项；仅「须拍板」项排队等待，不假借自治越过。

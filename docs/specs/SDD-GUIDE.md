# SDD-GUIDE：本仓库怎么写规格 / 防 spec drift

> **定位**：Spec-driven Development 落地的流程约定。承接文档宪法 v2 的同步纪律，升级为 SDD 流程。
> **参考**：ThoughtWorks SDD（2025-12）、GitHub Spec Kit、OpenSpec（归档不删）。

---

## 一、什么时候写 spec

任何**代码变更 / 架构演进 / 阶段施工**前，先在 `specs/tasks/` 落任务包（用 `_template.md`）：
- 外部行为写 Spec，不写实现细节
- 步骤写实现，可勾选
- 验收写可外部验证的勾选清单
- HITL 批点标注哪些需维护者拍板

## 二、spec 与实现分离 + Cursor 单线默认（2026-08-13）

- 先短 spec → 再实现 → 对照验收勾选 → 回写权威文档。
- 任务闭环后**归档 `specs/archive/` 不删**（OpenSpec：规范是长期资产）。
- `specs/tasks/` = 进行中；`specs/stages/` = 退出判据权威（常青）。

### 2.1 默认：Cursor 一气呵成（方案 + 编码 + 工程自验）

本仓库开发任务**默认**由 **Cursor** 在同一会话（或显式续聊）完成：

| 职责 | 谁 |
|------|-----|
| 起草 / 修订任务包与实现方案 | Cursor（或维护者口述后由 Cursor 落盘） |
| 落地改 `qi/` / 前端 / 测试 | Cursor |
| 工程自验（pytest / ruff / 对照验收栏） | Cursor |
| 回写 layers / progress / 相关 how-to | Cursor |
| 感受验证、阶段退出、架构/R 红线拍板 | **维护者**（HITL，不可代理） |

**纪律（防「边想边糊」）：**

1. **先落盘再大改码**：非琐碎改动先写/更新 `specs/tasks/` 任务包（至少 Spec + 验收 + HITL）；冻结范围类文件（如世界触达冻结）可当 Spec 真源。
2. **有疑先问**：触及人格契约、R1–R5、阶段判据、不可逆对外行动时，**停下来问维护者**，不擅自定路线。
3. **一次一包**：一个任务包一次合入意图；重构与行为变更不同包。
4. **薄过程稿**：默认**不**强制 `-PR方案` / `-交叉审查` / `-编码请求` / `-方案审查回复` / `-整改复审` 全套。需要对外可读或高风险时，可自选落盘 `-方案.md` 或完工 `-回执.md`（见 §2.3）。

### 2.2 过程稿落盘（仍要文件，不要靠粘贴长文）

- 进行中写在 `specs/tasks/`；闭环迁 `specs/archive/`。
- Agent **直接读目录**；维护者不必转发正文。
- **现行默认命名**（前缀 `YYYY-MM-DD-任务名`）：

| 文件 | 何时 |
|------|------|
| `.md`（任务包本体，四栏） | **始终**（或等价冻结/规格文 + 指针） |
| `-方案.md`（可选） | 改动面大 / 多文件 / 要维护者先看设计时 |
| `-回执.md`（可选） | 编码后要留下「改了什么 / 测了什么 / 偏离」 |
| `-验收记录.md`（可选） | 维护者或 Cursor 对验收栏做书面勾选时 |

> 旧双 Agent 后缀（`-PR方案`、`-Cursor交叉审查`、`-编码请求` 等）仅出现在 **archive 史料**；新包勿再当必做清单。

### 2.3 编码前自检（取代双轨硬闸）

默认顺序：

```
① 读代码 + 写/更新任务包（Spec / 验收 / HITL）
       ↓
② 聊天里列出关键改动点与风险；有 HITL 则等维护者一句放行
       ↓
③ 编码 + 测试
       ↓
④ 回写文档；需要时落盘回执；闭环后迁 archive
```

- **琐碎改动**（错字、单测断言、已拍板常量对齐）：可跳过完整任务包，但仍须防 drift 回写。
- **高风险 / 吃不准**：维护者可要求「先只写方案、先别动码」，或**可选**拉第二个 Agent **只审一页短方案**（顾问，不默认进流水线）。
- 包 16/17、N5-b 的教训仍成立：**方向未想清就开码会把错带进实现**——用「先短规格 + 有疑先问」承接，不用双 Agent 厚交接承接。

### 2.4 验收归属

- **工程验收**：Cursor 对照任务包验收栏自检（测试绿、纪律红线、范围未漂）。
- **感受 / 产品验收**：维护者（contract 软原则、相处手感、阶段退出）。
- 不再默认「另一家方案 Agent 做实施验收」；维护者若要书面工程验收，可让 Cursor 落 `-验收记录.md` 或亲自扫 diff。

## 三、阶段判据单一权威

- 退出判据以 `specs/stages/stage-*.md` 为唯一施工源。
- `explanation/栖·数字生命架构方案.md` §五 退为**摘要 + 链接**，不双源。
- C1–C5 定义全文留架构方案 §一；本仓库 `specs/acceptance.md` 只做**操作化 + 映射表**，链回 §一，不重写定义。

## 四、防 spec drift（核心纪律）

1. **常量/文件名/默认状态同步**（宪法第四节）：改代码常量、默认值、模块名、启用状态，必须排查 `docs/` 下所有写死同值处回写。
2. **机制文档以代码为准**：`reference/layers/` 与代码出入时回写 layers。
3. **定期审计**：每阶段退出复核，跑“文档 vs 代码”一致性扫描（断链/旧值/双源）。
4. **config 单源**：`reference/config.md` 以 `settings.example.yaml` 为真源，禁手抄默认值当第二权威（日限 1/3/20 教训）。

## 五、红线不双源

- R1–R5 全文留 `explanation/架构方案` §七；`specs/stages/_invariants.md` 只索引，不复制进 `reference/contract.md`，反之亦不可。
- 行为越界问 contract；工程纪律问 R 索引。

## 六、HITL 节点与决策路由表

规格评审、阶段退出、路线决策须维护者拍板；过程可自动。

### 6.1 决策路由表（谁拍板、谁自治）

为降低维护者阻塞频率，明确「可自治决策」与「必须维护者拍板」的边界。Agent 按此路由，**可自治项直接做并事后在过程稿标注「依惯例自动采纳，待维护者追认」；必须拍板项显式阻塞并 @维护者**。

| 决策类别 | 示例 | 路由 | 说明 |
|---------|------|------|------|
| **可自治（Cursor 直接定）** | 任务包起草、实现细节、工程自验、过程稿落盘、commit/push（维护者要求时）、临时日志清理 | Cursor | 阶段内常规推进不卡维护者 |
| **可自治（沿用已有倾向）** | 任务包 HITL 列表已标注且与既往拍板同类的推荐项、观察项后置式降级 | 依倾向/惯例自动采纳，事后追认 | 仅当倾向明确、无架构级分歧；否则升级为拍板 |
| **须维护者拍板（同步）** | 阶段退出、是否开新阶段、路线级决策（本地模型/真换心）、人格/不可逆能力边界、工作流改轨 | 阻塞 @维护者 | 产品负责人，路线不可自治 |
| **须维护者拍板（异步可接受）** | 收入定价校准、观察项落地节奏 | 可先记录，再择机拍板 | 不卡当前包推进 |

> **回写(2026-08-13)**：取消「方案 Agent 推荐项默认采纳」；HITL 由维护者本人定。Cursor 可在任务包标倾向供参考，**不**代替拍板。架构方向 / R1–R5 / 阶段判据仍须维护者拍板（见 §6.2）。  
> 旧注（2026-08-09 扩权）仅适用于当时双 Agent 流程，已废止。

### 6.2 自治的安全边界

- 可自治项不得悄悄改动「架构方向 / 红线 R1–R5 / 阶段判据」。若编码中发现触及这些，立即升级为拍板项。
- 「沿用已有倾向」仅适用于同阶段内已拍板过同类决策；跨阶段的新决策类型仍须拍板。
- 维护者不在时，可继续推进「可自治」项；「须拍板」项排队，不假借自治越过。
